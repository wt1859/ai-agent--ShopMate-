# ShopMate AI：面向 AI Agent 开发求职的工程路线图

> 本文把参考图中的能力类别映射到 ShopMate AI 的实际代码和后续学习路线。参考图描述的是一套更成熟的跨境客户经营 Agent 平台，不等于本仓库已经实现的功能。ShopMate AI 目前仍是可运行的本地学习 Demo；下文明确区分“已验证”与“规划”。

## 1. 参考图的能力画像

参考图聚焦的不是一个会聊天的 Bot，而是一组需要在真实业务中协同的工程能力：

1. **AI Native CRM**：客户事实、企业知识与记忆，服务商机分析、专家协作和受控动作；
2. **Agent Runtime 与持久执行**：执行内核、业务 Harness、SQL Worker、Run 状态、租约、取消、断点恢复和副作用保护；
3. **MCP 工具治理和多 Agent 协作**：工具 schema、租户和角色权限、读写分离、局部失败隔离；
4. **Context Engineering 与可信记忆**：按来源和权威性组织上下文，区分客户事实、知识证据、服务状态与推断；
5. **Agent Eval 和回归保护**：脱敏样本、确定性断言、语义评测、轨迹分析和规则变更回归。

这是一份很好的能力清单，但求职材料必须把“参考项目提出的能力”和“自己已经实现的能力”分开。不能把规划中的 MCP、Pi 内核、SQL Worker、Mem0 或 Langfuse 写成 ShopMate 已上线的功能。

## 2. 参考图与 ShopMate AI 当前状态

| 能力方向 | 当前代码证据 | 尚未实现/不可声称 | 建议下一步 |
|---|---|---|---|
| 客户事实与 CRM | `sessions`、`messages`、`orders`、`products` 和知识表使用 SQLite 演示数据 | 没有真实 CRM、WhatsApp、多租户客户档案或商机数据 | 先定义事实 schema、来源、租户边界和访问策略，再接 CRM API |
| Agent Harness | `DemoEngine.handle_message` 集中负责会话、意图、路由、检索/工具、回复和 Trace | 是同步的轻量 Demo 编排，不是独立长任务执行内核 | 将消息请求、Run 生命周期和工具执行职责分开 |
| 持久 Run | 会话、消息、trace、action 会存到 SQLite | 没有通用 Agent Run 状态机、checkpoint、租约、崩溃恢复、取消传播或幂等请求键 | 新建持久 Run/Event 记录，设计可恢复状态和重复请求测试 |
| SQL Worker | `Repository` 使用参数化 SQLite 查询演示订单/商品 | 没有独立 Worker 进程、SQL 计划校验、租户隔离或生产权限策略 | 设计只读 SQL Worker；写操作只能经白名单业务命令，不让 LLM 生成 SQL 直接执行 |
| 工具治理 | 订单/商品逻辑、待确认取消/退款和 `confirm_action` 可观察 | 还没有通用工具注册表、JSON Schema 契约、角色权限、租户作用域和统一审计 | 先建立 Pydantic 工具 schema、只读/写入分类、policy check 和审计轨迹 |
| MCP | 项目概念中讨论过工具调用 | 没有真实 MCP Server/Client、协议握手或 MCP 工具权限执行链 | 工具目录稳定后，增加一个本地 MCP server adapter，并用契约测试验证 |
| 专家/多 Agent 协作 | 当前有人工路由演示 | 没有专家 Agent 调度、共享上下文冲突解决或局部失败隔离 | 先做单 Agent + 确定性工具路由；只有真实工作流受益再加多 Agent |
| Context Engineering | 使用最近消息作为短期对话上下文；SQLite 保存会话和业务样例 | 没有 Mem0、跨会话个人画像、事实确认流程、来源权威等级或记忆撤销 | 分离 `conversation_context`、`customer_confirmed_facts`、`business_truth` 和 `knowledge_evidence` |
| 本地 Agent 评测 | `evals/cases.json` 保存 8 个离线场景；评测检查 intent、route、引用、trace 和安全状态；CI 可运行 | 不能代表线上准确率；不是 LLM-as-a-judge、Langfuse 数据集或真实模型 benchmark | 增加人工标注样本、Recall@k、任务成功率、工具错误和模型版本对比 |
| Trace 与监控 | trace 记录本地步骤、路由、决策和耗时，可在页面查看 | 没有 Langfuse、OpenTelemetry、集中式日志/指标或告警 | 先制定脱敏后的 Trace schema，再接可选的 Langfuse/OpenTelemetry exporter |
| 高风险操作 | Demo 先 `pending`，确认后改本地演示订单状态；测试确认前未改变订单状态 | 不连接真实交易服务，没有身份、订单归属或真实审批 | 在真实写工具前实现身份权限、业务规则、幂等键、操作审批和补偿方案 |

## 3. 当前已经能展示的 AI Agent 工程能力

下面这些内容以代码和自动化验证为依据，可作为项目介绍：

- **控制流而非只有聊天**：通过 Harness 风格的编排把意图决策、业务路由、检索、工具、确认和回复组成可读流程。
- **结构化意图和回退**：离线规则分类配合可选的 JEV 适配器；默认评测固定关闭外部 Provider，保证可复现。
- **业务数据与知识分离**：演示订单/SKU 由 SQLite 查询；政策类问题走检索并返回引用。
- **混合检索实验**：BM25 风格词法匹配、本地字符 TF-IDF 代理、RRF 排序和来源引用。明确标注本地代理不是生产向量检索。
- **Human-in-the-loop**：取消申请在确认前维持 `pending`，确认后只更新本地 Demo 状态；高风险动作不由一次 LLM 输出直接执行。
- **Trace 可观测性**：记录路由、意图、步骤和耗时，支持复现具体 Agent 行为。
- **Agent 行为回归**：新增版本化离线案例集，覆盖订单、SKU、售后、人工转接、多轮上下文、未知意图、促销和取消确认；断言包括安全状态。
- **前后端测试与 CI**：可以在干净环境自动运行后端测试、离线 Agent eval、前端测试和构建。

这些内容适合描述为“我实现/验证了一个 AI Agent 学习项目”。它们不能被描述成生产客户平台、企业级 CRM、真实 MCP 接入或线上客户服务经验。

## 4. 建议的迭代优先级

### P0：可复现的行为质量门禁（本轮已完成）

- 维护脱敏的合成案例和预期行为；
- 断言意图、路由、来源引用、trace 关键步骤和高风险操作状态；
- 固定使用本地规则、模板回复和本地检索代理，并断言 Provider/API Key 配置；常见 Python 网络 API 另有 best-effort tripwire，不把 Python monkeypatch 当成安全沙箱；若需强制零外连，须由运行环境配置并验证网络出口隔离；
- 把后端测试、Agent Eval、前端测试和构建纳入 CI。

**验收标准：**新开发者按 README 命令可从本地重现所有检查；评测失败时显示案例 ID 和具体断言。

### P1：Tool Registry 与授权策略

建议先将工具整理为显式契约：

```text
ToolSpec(name, input_schema, read_or_write, scopes, timeout, idempotency_policy)
   → PolicyEngine(principal, tenant, scopes, risk)
   → ToolExecutor
   → ToolResult + AuditEvent
```

先做本地 `query_order`（只读）和 `request_cancel`（写操作、必须审批）两个工具。测试无权限拒绝、越权租户拒绝、非法参数拒绝、确认前不写和重复请求不产生重复副作用。之后如确有需要，才把工具目录桥接为 MCP；**普通 Python 函数调用不应称为 MCP**。

### P2：持久 Agent Run 与恢复

设计 Run 状态机，而不是把 API 请求等同于整个任务：

```text
queued → running → waiting_approval → running → succeeded
                   ↘ failed / cancelled / interrupted
```

Run 记录至少应有：`run_id`、`session_id`、`request_id`、状态、版本、当前节点、checkpoint、租约过期时间、取消标记、工具调用引用、错误分类和时间戳。需要用集成测试模拟进程中断、重复投递、租约过期、恢复执行和“外部写入成功但确认响应丢失”的不确定状态。

SQLite Demo 可先模拟这一套持久状态；不要因此宣称已支持分布式 Worker。真正生产化时再考虑 Postgres、任务队列、outbox/inbox、租约竞争和故障演练。

### P3：Context Engineering 与事实来源

显式区分上下文块：

1. 本轮用户输入；
2. 当前会话最近对话；
3. 已核实的客户事实（来源、核实人、时间、有效期、撤销方式）；
4. 业务 SQL 返回的权威状态；
5. 企业知识及文档版本；
6. 模型推断或弱信号（明确标为非事实）；
7. 工具权限和本轮可执行动作。

排序和冲突策略必须明确。例如，当前订单系统状态应覆盖旧对话摘要；用户确认事实可以覆盖猜测性偏好；第三方导入知识必须保留来源和许可证，不可自动升级为商业授权。任何外部记忆库都应是受控的辅助投影，不应变成订单/客户身份的权威事实库。

### P4：进阶评测和外部观测

在确定性回归基础上逐步加：

- 多种表达和边界输入的意图分类集；
- 检索 Recall@k、MRR、引用精确率/忠实度；
- 工具选择与参数准确性；
- 任务完成率、确认率、拒绝率和人工转接率；
- provider/model/prompt 版本、延迟、Token 和成本；
- 脱敏后的 trace 导出和线上反馈回流。

引入 Langfuse 前先确定 PII 脱敏、保留期、租户隔离、访问控制与密钥管理；SDK 安装或 UI 截图本身不构成“可观测性已完成”。

### P5：真实系统集成

只有具备明确测试商户/沙箱、授权和安全边界后，才集成 CRM、WhatsApp、订单或物流服务。必须做到租户隔离、用户身份、工具最小权限、操作审计、幂等/补偿和人工接管。真实系统集成应与离线 Demo 的本地模拟模式分开配置、分开测试和分开描述。

## 5. 可直接用于简历/项目介绍的真实表述

### 一句话项目简介

**ShopMate AI：一个面向 AI Agent 工程学习的电商客服 Agent Demo，围绕意图路由、混合知识检索、业务工具、Human-in-the-loop 与可观测执行轨迹构建可复现的端到端闭环。**

### 项目经历 bullets

- 基于 **FastAPI、SQLite、Vue 3/TypeScript** 构建电商客服 Agent Demo，将意图识别、Harness 路由、知识检索、订单/商品查询和回复组装拆分为可观察的执行步骤。
- 实现 **离线 Agent 行为回归评测**：维护 8 个版本化合成对话场景，覆盖意图/路由、引用、Trace、多轮追问和高风险取消确认；评测强制使用本地 Provider，避免网络和账单依赖。
- 为取消/退款演示操作实现 **Human-in-the-loop 状态约束**，验证确认前保持待处理状态、确认后只更新本地演示数据；不将模型判断直接作为真实业务写入。
- 建立 **GitHub Actions CI**，自动运行后端测试、离线 Agent Eval、前端测试和生产构建；真实模型、CRM/MCP 和交易系统接入仍作为后续方向。

## 6. 面试讲解示例

> 我做的是 ShopMate AI，一个本地可运行的电商客服 Agent 工程 Demo。重点不是把一个 LLM 接到聊天框，而是把决策和执行控制拆开：用户问题先走意图路由，政策类进入混合检索并返回引用，订单和商品类通过本地业务数据查询，取消申请需要用户确认，整个过程会记录 trace。最近我补了一个不依赖外部模型的行为评测集，覆盖订单、商品、售后、多轮追问、人工转接和高风险确认，并接入 CI。当前实现是 SQLite 和本地规则/模板，不是生产 CRM、MCP 或持久化分布式 Run。下一步我会先做工具权限和幂等，再做可恢复 Run 状态机，用失败恢复测试证明可靠性。

### 常见追问

**为什么还没有上多 Agent？**

> 目前单 Agent + 显式业务路由足以表达 Demo 的路径。多 Agent 会引入共享状态、权限和失败协调成本；我会先证明单 Agent 工具契约和评测覆盖不足，再在有清晰边界的专家任务上引入协作。

**你项目里的 MCP 做了什么？**

> 目前没有实现 MCP 协议。现阶段是本地工具/Repository 调用；我把 MCP 作为后续标准化工具边界的方向，不会将普通函数调用说成 MCP。

**如何保证长任务恢复？**

> 当前版本还不支持通用长任务恢复。下一步计划持久化 Run、节点 checkpoint、幂等 request/tool ID、租约、取消和等待审批状态，并测试“中断后恢复”与“写入成功但响应丢失”的情况。

**8 个评测案例说明准确率是 100% 吗？**

> 不是。它只说明这 8 个固定合成案例在本地规则和模板模式下全部满足断言。它不是线上准确率，也不能证明真实模型或未见表达的泛化表现。

## 7. 面向 Agent 开发岗位的学习顺序

1. 逐函数理解 `DemoEngine.handle_message` 和 SQLite Repository；
2. 阅读并扩展 `demo/backend/evals/cases.json`，掌握行为回归设计；
3. 为工具增加 schema、权限、审计和幂等测试；
4. 加入持久 Run 状态机与故障恢复测试；
5. 实现事实分层、来源可信度、作用域和过期策略；
6. 学习 MCP server/client 的协议和安全边界，再做适配器；
7. 增加真实模型评测、检索评测和可观测性；
8. 在经过授权的沙箱中验证真实业务集成。

这条路线能将项目从“客服 Demo”逐步扩展成一个可以讨论 Agent Runtime、工具治理、上下文、可靠性与评测的工程作品，同时保持所有简历表述可由代码和测试证据支撑。
