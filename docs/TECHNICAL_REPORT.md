# ShopMate AI 技术报告

> 本报告描述的是仓库中已经发布的 `demo/`，不是把本地旧目录里的空白骨架当成已完成系统。报告中的“已实现”指当前 Demo 中可以运行、测试或从代码中明确验证的部分；“生产建议”指后续接入真实电商系统时需要补充的能力。

## 1. 项目摘要

ShopMate AI 是一个用于学习电商智能客服 Agent 架构的本地 Demo。它没有把所有工作交给一个聊天模型，而是将客服请求拆成多个可以观察和验证的步骤：

```text
用户消息
  → 会话与上下文
  → 意图判断
  → 业务路由
  → 知识检索或业务工具
  → 风险确认（必要时）
  → 回复生成
  → 引用、轨迹与结果持久化
```

项目适合学习以下问题：

- 普通客服机器人和 Agent 的区别是什么；
- JEV/决策模型为什么不等于聊天模型；
- LLM、RAG、工具调用和流程控制如何组合；
- 为什么订单、库存、物流等信息不能只依赖模型记忆；
- 为什么退款和取消订单需要确认和业务校验；
- 如何记录 Agent 的决策、路由、耗时和回退情况。

当前 Demo 默认不需要任何外部 API Key，可以在本地运行。它使用 SQLite、种子数据、本地规则、模板回复和字符 TF-IDF 检索代理，因此重点是帮助学习架构，而不是宣称已经完成生产级电商接入。

## 2. 与传统电商客服的区别

这里的“传统客服”包含两类常见系统：人工坐席配合 FAQ/工单系统，以及基于关键词和固定流程的客服机器人。ShopMate AI 不是简单地把 FAQ 换成聊天窗口，而是加入了决策、检索、工具和可观察执行链路。

| 对比维度 | 传统人工/规则客服 | ShopMate AI Demo | 带来的变化 |
|---|---|---|---|
| 问题理解 | 依赖人工判断，或匹配固定关键词 | 先做意图判断，再选择流程 | 同一问题可以从不同说法进入同一业务路由 |
| 回复方式 | 人工查模板，或返回固定话术 | 结合检索结果、工具结果和上下文生成回复 | 回复可以根据当前问题组织，但仍受资料约束 |
| 知识获取 | 人工搜索 FAQ 或维护大量规则 | 混合检索并返回引用 | 方便解释“答案来自哪里” |
| 实时数据 | 坐席手动查询后台 | 通过订单、商品等业务工具读取结构化数据 | 价格、库存、订单状态可以与知识回答分开处理 |
| 多轮对话 | 依赖坐席记忆或简单 session | 保存会话消息，最近消息参与决策 | 能处理“那已经发货了呢？”这类追问 |
| 流程控制 | 由坐席经验或写死流程决定 | Harness 负责路由、步骤和轨迹 | 模型输出不会直接等于业务执行 |
| 高风险操作 | 人工确认，或由后台权限控制 | 先生成 pending 操作，再要求确认 | 降低误取消、误退款的风险 |
| 人工转接 | 坐席接管，系统可能缺少上下文 | 识别投诉/人工意图并记录 handoff 路由 | 可以保留决策和前置上下文 |
| 可观测性 | 主要看聊天记录和工单 | 记录 decision、route、steps、耗时和引用 | 便于调试和评估每一步 |
| 统一性 | 受不同坐席经验影响 | 模板、规则和系统提示词提供统一边界 | 更容易形成可测试的服务标准 |
| 灵活性 | 人工处理边界问题更强 | 对自然语言和新表达更灵活 | 减少纯规则系统的规则爆炸 |
| 可靠性 | 人工成本高但复杂判断灵活 | 模型可能误判，必须配合校验和回退 | 需要评测集、阈值、人工兜底和审计 |
| 成本结构 | 人力成本占主导 | 增加模型、检索、服务和监控成本 | 可能降低重复问答成本，但不是零成本 |
| 延迟 | 取决于坐席响应速度 | 依赖模型、检索、数据库和网络 | 自动回复通常更快，但外部模型可能抖动 |

### 2.1 不能简单说“Agent 一定优于传统客服”

Agent 的优势是理解范围更宽、流程可以组合、工具可以提供实时数据；它的代价是系统复杂度和错误模式增加。传统规则系统在范围固定、风险高、结果必须可预测的场景中仍然有价值。

比较合理的实际形态通常是混合模式：

```text
简单 FAQ        → 自动检索和回复
实时订单问题    → 调用业务工具
退款/取消       → 规则校验 + 用户确认 + 权限校验
复杂投诉        → 保留上下文后转人工
模型不确定      → 回退规则或人工
```

## 3. 为什么采用这套技术

### 3.1 采用 Harness，而不是直接把问题交给 LLM

如果只把用户输入放进 LLM，模型可能会生成一段听起来合理的文字，但系统无法稳定回答以下问题：

- 它判断的意图是什么；
- 为什么调用了这个工具；
- 查询的订单号是否属于当前用户；
- 退款是否经过确认；
- 模型失败后是否有回退；
- 这次回复用了哪些知识资料。

Harness 在这里是 Agent 的运行时和控制层。它不负责替代模型，而是负责把模型、检索、工具和安全门组合成可执行流程。当前 Demo 中，`DemoEngine` 负责会话读取、意图判断、路由、检索、订单/商品处理、待确认操作、回复保存和 trace 保存。

### 3.2 采用意图路由，而不是让 LLM 直接决定所有业务动作

电商问题通常有明确业务类别：物流、订单、商品、售后、退款、投诉和人工。先把问题映射到有限的意图集合，可以让后续流程更稳定：

```text
物流查询  → 订单/物流查询工具
商品咨询  →  商品工具 + 商品知识
售后咨询  →  售后知识检索
投诉      →  人工转接流程
取消订单  →  身份校验 + 业务规则 + 明确确认
```

当前 Demo 默认使用本地规则，原因是没有外部依赖也能运行和复现；JEV 适配器则用于学习结构化决策模型如何从候选意图中做选择。

### 3.3 采用 JEV/typed decision 的原因

JEV 的角色是“做决策”，不是“写长文本”。它适合回答：

```text
给定用户问题和候选意图，最可能是哪一个？
是否需要人工介入？
问题紧急程度是多少？
```

这比让聊天模型自由生成 `{"intent": "..."}` 更容易约束候选项，也更容易比较概率和评测准确率。无论使用真实 JEV 还是本地规则，决策结果都应该交给 Harness 和业务层继续校验，不能因为模型选择了 `refund_request` 就直接发起真实退款。

### 3.4 采用 LLM 的原因

LLM 更适合把已经确认的事实组织成自然语言，例如：

- 把订单工具返回的数据解释给用户；
- 根据知识库片段生成易读答案；
- 处理上下文中的指代和追问；
- 在不确定时明确说明需要核实。

因此项目把“决定走哪条流程”和“如何表达回复”分开。没有配置 LLM 时，Demo 使用模板回复；这使得架构仍然可运行，也不会把离线模板伪装成真实模型调用。

### 3.5 采用 RAG 和引用的原因

售后政策、发货规则和活动说明属于知识问题，模型本身不应该凭记忆回答。RAG 先从知识库召回相关内容，再把内容提供给回复层。当前 Demo 将引用随回复返回，并在 trace 中记录检索步骤。

这样做的主要价值是：

- 减少模型自由编造政策的空间；
- 让回复可以追溯到具体资料；
- 知识更新时不必重新训练模型；
- 可以按知识域路由，例如售后、物流、商品和人工服务。

### 3.6 采用混合检索，而不是只用一种检索

电商场景同时存在两种查询：

- “七天无理由退货吗？”这类语义和政策问题；
- “SKU-PHONE-001”“DEMO20261017001”这类必须精确匹配的标识符问题。

只使用向量检索可能漏掉精确编号，只使用关键词又可能无法处理表达变化。因此 Demo 使用：

```text
关键词/BM25 风格匹配
        +
本地字符 TF-IDF 相似度代理
        ↓
RRF 排名融合
        ↓
分数重排
```

要注意，当前字符 TF-IDF 是为了离线学习的轻量代理，不是生产级 embedding。生产环境可以替换为真实 embedding、BM25/OpenSearch/Elasticsearch、向量数据库和 reranker，但接口职责可以保持不变。

### 3.7 采用工具层，而不是让模型猜订单状态

模型不知道实时库存、订单状态和物流轨迹。把这些能力做成工具后，系统可以让模型决定“需要查询什么”，再由业务服务返回真实结构化数据。生产环境还必须增加：

- 用户身份和订单归属校验；
- 权限校验；
- 工具参数校验；
- 幂等键和重复提交保护；
- 超时、重试和审计；
- 对退款、取消等动作的服务端二次验证。

当前 Demo 用 SQLite 和种子订单模拟这一层，目的是展示边界，不代表已经接入真实业务。

### 3.8 采用确认门和人工兜底

退款、取消、投诉等请求不能只依赖一次模型判断。当前流程先创建 `pending` 演示操作，用户确认后才更新本地演示状态；投诉和明确人工请求则路由到 `human`。

这体现了 Agent 系统的一个基本原则：

> 模型可以提出下一步建议，但高风险动作必须由业务规则、权限和确认机制共同决定。

### 3.9 采用 trace 的原因

没有 trace，Agent 出错时只能看到一句最终回复，无法判断问题来自意图、检索、工具还是生成层。当前 trace 至少记录：

- decision：意图、域、置信度、provider、是否需要人工、紧急度；
- route：最终进入的业务路线；
- steps：规范化、意图判断、订单查询、商品查询、知识检索、人工门等步骤；
- duration_ms：单次处理耗时；
- citations：返回的知识引用。

生产环境可以继续接入 OpenTelemetry、日志系统、指标系统、模型评测和人工反馈。

| 技术 | 当前用途 | 状态 |

### 4.3 Agent 编排层

1. **会话管理**：创建、读取、删除会话，保存用户和助手消息。
2. **短期上下文**：读取最近消息，将其传给意图判断和可选 LLM。
3. **消息规范化**：去除首尾空白并拒绝空消息。
4. **意图决策**：在有限意图集合中选择主意图。
5. **路由决策**：根据意图选择 `orders`、`product`、`knowledge`、`human` 或 `knowledge+orders`。
6. **工具/检索执行**：按路线调用订单、商品或检索逻辑。
7. **结果组装**：把业务结果、引用和安全提示组装成回复。
8. **操作状态机**：操作从 `pending` 进入 `confirmed`，订单演示状态变为 `cancel_requested` 或 `refund_requested`。
9. **执行轨迹**：保存步骤、路由、决策和耗时。
10. **失败回退**：外部 JEV、LLM 或 Embedding 调用失败时回到本地实现。

### 4.4 决策与 NLU

- **本地规则分类**：通过关键词分数完成离线意图判断。
- **JEV 适配器**：将消息、最近历史和候选意图组装为结构化决策请求；当前代码读取 `TYPESAFE_API_KEY` 后才尝试远端调用。
- **Choice decision**：从候选意图中选择一个结果。
- **Noul decision**：判断是否需要人工介入。
- **Score decision**：估计紧急程度。
- **置信度**：用于记录决策可信程度和 trace 状态。
- **多意图标记**：检测用户表达是否同时命中多个意图。
- **实体抽取**：当前 Demo 用正则提取订单号和 SKU，而不是独立的模型实体抽取服务。
- **会话上下文**：当当前消息没有明显关键词时，尝试使用最近消息辅助判断。

当前支持的主要意图包括：

```text
product_consult   商品咨询
order_query       订单查询
logistics         物流查询
refund_return     退款/退货/取消
payment           支付相关
promotion         优惠活动
complaint         投诉
human_agent       转人工
other             其他或无法判断
```

### 4.5 知识库和 RAG

- 知识条目：标题、正文、类别、来源、版本、更新时间。
- 知识域：`after_sales`、`logistics`、`payment`、`product`、`promotion`、`human`。
- 关键词切分：英文/数字 token 和中文双字片段。
- BM25 风格评分：使用词频、文档频率和长度归一化。
- 本地 dense 代理：字符/词项 TF-IDF 加余弦相似度。
- 可选 Embedding：通过 OpenAI-compatible `/embeddings` 接口请求向量。
- RRF：融合 lexical 和 dense 两套排序。
- 二次评分：综合 RRF、dense 分数和词法分数。
- Top-k：限制返回数量并形成引用。
- Citation：把知识条目 ID、标题、正文、来源和分数带回调用方。
- 回退：远端 Embedding 失败时回到本地计算。

### 4.6 业务工具

当前 Demo 里的工具能力通过后端逻辑和 SQLite Repository 表现：

- 查询订单；
- 查询物流单号和状态；
- 查询商品、价格和库存；
- 查询售后、支付、物流和促销知识；
- 生成取消订单演示申请；
- 生成退款/退货演示申请；
- 转人工演示路由；
- 查询历史消息和执行轨迹。

需要明确：当前 Demo 没有真正连接 ERP、OMS、WMS、支付网关、物流平台或人工坐席系统。

### 4.7 记忆与状态

- **短期记忆**：最近 8 条消息。
- **会话状态**：会话 ID、标题、状态、更新时间和消息数量。
- **消息状态**：用户/助手角色、内容、trace、引用和 actions。
- **业务状态**：订单状态、商品库存和知识版本。
- **动作状态**：待确认、已确认。
- **持久化方式**：SQLite 表和 JSON 字段。

这属于轻量级会话记忆，不等于长期用户画像、向量记忆或跨会话个性化记忆。

### 4.8 安全与控制

当前已实现的安全边界：

- 退款/取消不直接执行；
- 确认后仍只修改本地演示数据库；
- 回复中明确说明没有连接真实订单或支付系统；
- 外部 API Key 使用环境变量，不写入代码；
- HTTP 请求字段有长度限制；
- 不把本地数据库、虚拟环境和构建目录提交到仓库。

生产环境仍必须增加：

- 登录、用户身份和订单归属检查；
- RBAC/ABAC 权限控制；
- PII 脱敏和加密；
- 工具白名单和参数 schema；
- 速率限制、重放保护、幂等键；
- 审计日志和审批流；
- Prompt injection、数据外泄和越权工具调用防护；
- 模型输出校验和敏感内容过滤。

### 4.9 可靠性与可观测性

当前有：

- 外部 provider 失败后的本地回退；
- 请求参数校验和 HTTP 错误响应；
- 业务步骤状态 `ok` / `fallback`；
- trace 中的耗时、路由和步骤；
- 测试覆盖核心离线路径。

生产还需要：

- 结构化日志；
- 指标：成功率、P95 延迟、工具错误率、转人工率、回退率；
- 分布式 trace；
- 告警；
- 模型版本和 Prompt 版本管理；
- 线上反馈闭环；
- 回归评测集和灰度发布。

## 5. 一次请求的完整执行过程

以“查询订单 DEMO20261017001 的物流”为例：

1. 前端发送 `session_id` 和 `content`。
2. FastAPI/Pydantic 检查字段不为空且长度合规。
3. `DemoEngine` 检查会话是否存在。
4. `JevClassifier` 先尝试配置的远端 JEV；没有配置时使用本地规则。
5. 系统识别为 `logistics` 或 `order_query`。
6. 路由切换到 `orders`。
7. 正则抽取订单号 `DEMO20261017001`。
8. Repository 从 SQLite 查询订单。
9. 返回订单状态、商品、金额和物流单号。
10. 检索物流知识条目作为引用。
11. 生成包含“演示数据”说明的客服回复。
12. 将用户消息、助手消息、引用和 trace 持久化。
13. 前端展示回复、引用、决策和执行步骤。

以“取消订单 DEMO20261017002”为例，流程会在第 11 步先生成待确认 action，而不是立即更新订单。只有用户点击确认后，才把本地 action 改为 `confirmed`，把演示订单改为 `cancel_requested`。

## 9. 推荐的学习顺序

1. 先运行离线 Demo，观察订单查询、知识问答和取消确认。
2. 阅读 `demo/backend/demo_service/engine.py`，跟踪一次消息如何进入 `handle_message`。
3. 对比 `JevClassifier._local` 和 `_remote`，理解规则决策与结构化模型调用的差异。
4. 阅读 `HybridRetriever.search`，理解 BM25 风格匹配、TF-IDF、RRF 和引用。
5. 阅读 `Repository.confirm_action`，理解高风险动作为什么要经过确认。
6. 修改知识库种子数据或新增测试，观察路由和检索变化。
7. 再尝试接入一个兼容的 LLM，比较模板回复和模型回复。
8. 最后建立意图评测集，比较规则、Open-Jev/JEV 和普通 LLM 的准确率、延迟和成本。

## 10. 结论

ShopMate AI 与传统客服的主要区别，不是“用了一个更大的模型”，而是把客服从单一问答拆成了一个可控的 Agent 工作流：

```text
决策模型负责判断
Harness 负责控制
RAG 负责找资料
业务工具负责查事实
LLM 负责组织语言
安全层负责限制动作
Trace 负责解释过程
```

这套拆分适合学习，也更接近真实业务系统的设计方式。但当前仓库仍然是本地 Demo。只有在接入真实业务 API、身份权限、生产检索、模型评测、审计和监控后，才能进一步讨论生产可用性。
